# BrownDust2 戦闘シミュレータ概念設計

仕様基準日: 2026-09-01（Asia/Tokyo）

対象: 基準日時点の最新ゲーム仕様のみ

方針: 旧仕様との後方互換、旧データの移行、旧ルールの再生は実装しない

## 1. 目的

本システムは、BrownDust2 の戦闘を、同じ初期状態・入力・乱数列に対して同じイベント列、HP、SP、座標、効果、勝敗、得点を返す純粋なシミュレータとして再現する。通常PvEだけでなく、鏡戦争、ゴールデンコロシアム、魔物追跡者、ギルドレイド、終末の書、悪魔城、マルチフェーズ戦闘、四魂の盤を同じ戦闘プリミティブから構成できることを目標とする。

「画面上の最終ダメージが近い」だけでは再現完了としない。各ヒット、チェイン、クリティカル、効果の付与・解除・失効、割り込み、死亡、復活、ノックバック、SP、クールタイム（以下CT）まで一致させる。

UI、演出、音声、通信、課金、報酬受け取りは対象外とする。ただし、参加回数、ボスレベル、日次保存、レーティングなど、次の戦闘の初期状態や最終得点を変えるメタ状態はモードアダプターの対象に含める。

## 2. 設計原則

### 2.1 現行仕様を一つだけ持つ

- `ruleset_id` は `bd2-current-2026-09-01` の一つとする。
- 旧仕様向けの条件分岐、互換フラグ、マイグレーションコードは作らない。
- 公式更新で仕様が変わった場合は、ルール、データ、受け入れトレースを同時に現行版へ置換する。
- シーズンやボスごとに異なる値は「旧仕様」ではなく現行コンテンツデータである。盤面、初期SP、SP回復、ターン上限、ボス行動表、ゴールデンコロシアムのシーズンルールなどを遭遇定義として渡す。

### 2.2 戦闘ロジックとデータを分離する

システムを次の4層に分ける。

1. **現行データスナップショット**: キャラクター、コスチューム、スキル、バースト、成長、装備、敵、ボス、遺物、加護、ステージ。
2. **戦闘コア**: 盤面、対象解決、イベント、算術、効果、死亡、乱数。
3. **モードアダプター**: 行動単位、先後、SP、CT、チェイン、編成人数、勝敗・得点、永続状態。
4. **環境API**: 初期化、観測、合法手、遷移、終了判定、ログ、保存・復元。

新しいコスチュームやボスは原則としてデータ追加で表現する。新しい処理型が必要な場合だけ戦闘コアの命令セットを増やす。

### 2.3 すべてをイベントとして確定順に処理する

攻撃を一つの関数でまとめて処理せず、`ACTION_DECLARED`、`TARGET_LOCKED`、`HIT_STARTED`、`DAMAGE_COMPUTED`、`DAMAGE_APPLIED`、`CHAIN_CHANGED`、`UNIT_DIED` などのイベントへ分解する。イベントは単調増加する `sequence_no` を持ち、同じ優先度では安定したID順ではなく、現行クライアントで確認した明示的なタイブレーク規則を使う。

### 2.4 算術は浮動小数点を使わない

割合は整数分子・分母または固定小数点で保持する。クライアントが小数点以下を切り捨てる各境界で明示的に `floor` を行う。計算式を代数的にまとめると途中丸めが変わるため禁止する。

## 3. 用語と時間軸

| 用語 | 定義 |
|---|---|
| キャラクター | 同一人物としてHP、位置、装備、複数コスチュームを共有する通常戦闘の行動主体 |
| コスチューム | スキル、SP、CT、範囲、強化、潜在力、バーストを持つ衣装単位の能力 |
| 駒 | 盤面上の占有主体。通常戦闘ではキャラクター、ゴールデンコロシアムではコスチューム、ボス戦では部位ノードを含む |
| チーム手番 | 通常戦闘で一陣営が行動計画を決め、予約した全員の行動を解決する区間 |
| ゲームターン | 通常戦闘の表示上のターン。味方手番を1、敵手番を2、次の味方手番を3と数える |
| ALLターン | ゴールデンコロシアムで先手1体と後手1体が行動した後に1増える時計 |
| アクション | 1駒が行う通常攻撃、ノックバック、コスチュームスキル、強制行動、待機 |
| ヒット | アクション中の1回の命中・回避・ダメージ・効果判定単位 |
| フェーズ | 同一遭遇内で敵構成、行動表、盤面、勝利条件が切り替わる区間 |
| エピソード | 1回の `reset` から勝敗・得点確定まで。複数編成や複数フェーズを含められる |

時間は単一の `turn` に押し込めず、次を別々に保持する。

```text
episode_step        環境APIへ入力された意思決定回数
game_turn           通常戦闘のチーム手番ごとの表示ターン
round_no            双方が一巡した回数
all_turn            ゴールデンコロシアムの双方1体行動後の時計
action_sequence     戦闘全体のアクション通番
event_sequence      イベント通番
phase_no            現在フェーズ
party_wave_no       魔物追跡者などの編成交代番号
```

効果ごとに `duration_clock` を持たせ、`GAME_TURN`、`ALL_TURN`、`ACTION`、`ROUND`、`PHASE`、`PERMANENT` のどの時計で減るかを定義する。これにより「4ターン」を一律に誤解しない。

## 4. 盤面と座標

### 4.1 標準盤面

通常戦闘は各陣営が独立した3行×4列の盤面を持ち、最大5キャラクターを配置する。座標は陣営ローカルで次のように定義する。

- `row`: 上から `0..2`
- `depth`: 敵に近い最前列を `0`、最後列を `3`
- `side`: `A` または `B`

両陣営で「前」を `depth` の減少方向に統一する。表示座標への変換時だけ片側を鏡映する。対象検索と範囲回転を画面座標へ依存させない。

### 4.2 可変盤面

`GridDefinition` は行数、列数、配置上限、使用不可セル、初期占有、向き、複数セル駒を定義する。ゴールデンコロシアムは現行ルールの5×5・9コスチュームを使用する。四魂の盤は駒と床に向きを持たせる別グリッドアダプターを使用する。

### 4.3 占有規則

- 通常の駒は1セルを占有し、同じ陣営の同じセルに2駒は存在できない。
- 戦闘不能になった駒は占有を直ちに解放する。ただし、復活予約や召喚のために論理IDは残す。
- 多部位ボスは「本体HP」と「ターゲット可能な部位ノード」を分離する。部位は同じ本体HPへダメージを送れる一方、部位ごとに座標、弱点倍率、効果、チェイン、デバフ、破壊状態を持てる。
- 複数セルボスは占有セル集合と、ターゲットアンカー集合を別に持つ。

## 5. 静的データモデル

### 5.1 キャラクターとコスチューム

```text
CharacterDefinition
  character_id
  element: FIRE | WATER | WIND | LIGHT | DARK | NONE
  attack_type: PHYSICAL | MAGICAL
  base_growth_table
  targeting_profile: FRONT | SKIP | custom
  normal_attack_definition
  knockback_definition
  costume_ids[]

CostumeDefinition
  costume_id, character_id
  skill_variants[enhancement_level][potential_state][burst_level]
  preemptive_skill
  cooldown
  sp_cost
  range_pattern
  hit_program
  effect_program
  tags[]
```

通常戦闘では同一キャラクターを1体として編成し、所有コスチュームのスキルを切り替えて使う。各コスチュームのCTは別に保持する。ゴールデンコロシアムではコスチューム自体が独立した駒であり、同一キャラクターの別コスチュームを同時配置できる。

### 5.2 成長値

戦闘開始時のステータスは、モードが許可した層だけを次の順で合成する。

```text
レベル基礎値
→ 固定加算成長
→ 割合成長
→ コスチューム結束
→ 潜在力
→ 刻印
→ 覚醒
→ コスチューム強化
→ バースト解放
→ 装備・専用装備
→ コレクション等のアカウント効果
→ モード補正（遺物、加護、塔、難易度）
→ 戦闘開始時効果
```

各層を一つの合計値にせず、`StatContribution` として発生源、カテゴリ、固定/割合、対象、優先順を保存する。ゴールデンコロシアムは装備層を除外し、結束、潜在力、レベル、刻印、覚醒、コスチューム強化、バーストを反映する。

### 5.3 ステータス

最低限、次を保持する。

- 最大HP、現在HP
- 攻撃力、魔法力
- クリティカル率、クリティカルダメージ
- 防御力、魔法抵抗
- 属性、属性ダメージ増加
- 与ダメージ増減、被ダメージ増減、増強、脆弱
- チェインダメージ、チェイン加算数
- 回復量増減、被回復量増減
- 通常攻撃・スキル・固定・継続・反撃・衝突などの種別補正
- SP消費増減、SP獲得増減
- CT増減
- ノックバック距離・方向・耐性
- 効果成功/耐性が存在する場合の値

表示値 `raw_stat` と、上限・下限を適用した `effective_stat` を分離する。防御力・魔法抵抗はデバフ計算前の表示値が90%を超え得るが、ダメージ計算に用いる実効上限は90%とする。

### 5.4 バースト

バーストは通常スキルへの単純なダメージ倍率ではない。0（不使用）と解放済みの1～3段階を別スキル派生として扱う。

- 段階ごとの追加SPを基礎SPへ加算する。
- 段階ごとに倍率、打撃数、範囲、主対象、効果、条件、チェイン、SP操作が変化できる。
- バースト不可コスチュームを表現する。
- 行動カードとログに使用有無・段階を残す。
- 合法手は所有、解放段階、SP、沈黙、モード制約から生成する。

`BattleState` は次を完全にシリアライズできなければならない。

```text
BattleState

  data_snapshot_digest
  encounter_id, mode_id
  clocks
  active_side, first_side
  phase_state, wave_state
  grids[side]
  units[unit_id]
    identity, alive, hp, max_hp, position
    computed_stats, stat_contributions
    costume_cooldowns
    active_effects[]
    shield_layers[]
    action_history
    revival_state
  team_state[side]
    sp, sp_cap
    action_queue
    formation_lock
    shared_effects[]
    chain_state_by_target
  boss_state
    monster_id, selected_level, progress_level
    battle_hp_remaining, cumulative_damage
    cumulative_hp_thresholds[], incremental_hp_segments[]
```

状態には計算済みキャッシュだけでなく、その値を作った寄与を残す。状態復元後に同じイベント列を継続できるよう、未処理イベント、乱数位置、対象ロック、ヒット番号も保存する。

## 7. 行動モデル

### 7.1 意思決定点

通常戦闘の1回の入力は、次のチーム手番計画を表す。

```text
TeamTurnPlan
  formation: unit_id -> cell
  order: unit_id[]
  commands:
    unit_id ->
      NORMAL_ATTACK
      KNOCKBACK
      USE_COSTUME_SKILL(costume_id, burst_level)
      PASS                 # モードまたは強制状態が許す場合だけ
  commit: true
```

行動対象は通常、任意クリックで選ぶのではなく、行動者のターゲット種別、行、挑発・集中・ロックオン、盤面から決定する。したがってアクションは主対象IDを原則として持たない。例外的にプレイヤーが部位や対象を明示選択できるコンテンツだけ `target_selector` を公開する。

### 7.2 合法性

`legal_actions(state, side)` は行動マスクと理由を返す。

- 生存、行動可能、編成制約を満たす。
- スキルのCTが0である。
- 沈黙などの禁止効果を受けていない。
- 基礎SPとバースト追加SPを支払える。
- 対象または対象セルが存在する。
- コスチューム、強化、潜在力、バーストを所有・解放している。
- モードが通常攻撃、ノックバック、スキル、配置変更を許している。

予約時に合法でも、実行前の死亡、沈黙、SP減少、対象消滅で不可能になる場合がある。`on_illegal_at_execution` をモードに定義し、`SKIP`、`NORMAL_ATTACK`、`RETARGET` のいずれかへ決定的にフォールバックする。オート戦闘の不発処理を人間向けUIへ依存させない。

### 7.3 通常攻撃とノックバック

- 通常攻撃はキャラクター定義の攻撃型、倍率、範囲、打撃数を使い、完了時に基礎SPを1獲得する。
- ノックバックは対象へ基礎1ダメージを与え、定義された8方向と距離で移動を試み、完了時に基礎SPを1獲得する。
- ノックバック付きコスチュームスキルは通常のノックバック行動とは別であり、スキル側のダメージ、SP、チェイン、移動命令に従う。
- SP獲得はアクション開始ではなく、現行クライアントで確認した完了イベントに結び付ける。死亡・不発時の獲得可否もイベントログで固定する。

## 8. 対象選択と範囲

### 8.1 主対象

敵を対象とする標準解決は次の順で行う。

1. 強制対象効果（挑発、集中、ロックオン等）の候補を、効果の優先順位と有効性で解決する。
2. 強制対象がなければ行動者と同じ `row` の対象候補を前方から列挙する。
3. 同じ行が空なら、現在行の一つ下から下方向へ進み、端を越えたら最上行へ戻る循環順で、最初に敵がいる行を選ぶ。
4. `FRONT` は前から1体目、`SKIP` は前から2体目を選ぶ。同じ行に1体だけなら `SKIP` もその1体を選ぶ。
5. 対象不能、ステルス、無敵、部位選択制限などを適用する。
6. 主対象をロックし、範囲パターンのアンカーとする。

手順3と強制対象の競合順は実機受け入れトレースで固定する。実装では探索順を暗黙の配列順にしない。

### 8.2 範囲

範囲はアンカーからの相対セル集合として保持する。

```text
RangePattern
  anchor: MAIN_TARGET | SELF | CELL | BOSS_PART
  offsets: (dr, dd)[]
  orientation: TOWARD_ENEMY | FIXED | UNIT_FACING
  include_anchor
  target_side: ALLY | ENEMY | BOTH
  acquisition: SNAPSHOT_AT_CAST | REEVALUATE_EACH_HIT
```

主対象追加ダメージ、副対象、空セル、途中死亡、召喚物、複数セルボスを区別する。対象列の順序はヒット・効果の割り込み順へ影響するため、`row`、`depth`、主対象優先など、スキル定義で明示する。

## 9. 標準戦闘の進行

### 9.1 初期化

1. 現行データと遭遇定義の整合性を検証する。
2. モードに許可された成長層から開始ステータスを計算する。
3. 盤面へ駒とボス部位を生成する。
4. モードの初期SP、上限、先後、ターン、チェイン規則を設定する。
5. 常時効果、オーラ、遺物、加護、難易度補正を登録する。
6. 先制発動スキルを所定の順序で解決し、必要ならSPを支払う。
7. 戦闘開始トリガーを解決する。
8. 最初の意思決定点まで内部イベントを進める。

### 9.2 チーム手番

1. `TEAM_TURN_STARTED` を発火する。
2. モード指定のSP回復、CT減算、継続効果、条件スキルを解決する。
3. 操作可能なら配置、順序、行動予約を受け取る。オート側は保存済み計画または決定方策から生成する。
4. 予約順に各駒の行動可否を再評価し、1体ずつアクションを完全に解決する。
5. 各アクション後に死亡、勝敗、フェーズ、強制終了を評価する。
6. `TEAM_TURN_ENDED` を発火し、ターン終了効果と失効を解決する。
7. 勝敗未確定なら相手へ手番を渡し、`game_turn` を進める。

一般PvEは味方が先手で、基準初期SPは15とする。通常PvEに毎ターン共通の自然SP回復を仮定せず、通常攻撃・ノックバック・スキル効果・遭遇定義から増減させる。魔物追跡者やギルドレイドのターン回復SPはボス定義に持たせる。

### 9.3 アクション解決

標準イベント順は次のとおりである。

```text
ACTION_DECLARED
→ legality recheck / fallback
→ SP_COST_MODIFIED
→ SP_PAID
→ TARGET_LOCKED
→ CAST_STARTED
→ pre-cast / pre-attack effects
→ for each hit:
     HIT_STARTED
     → targets acquired
     → accuracy/evasion/critical rolls
     → pre-damage effects
     → damage or healing computed
     → barrier/guard/HP applied
     → chain updated
     → on-hit / on-damaged triggers
     → death and revival checkpoint
     → movement/knockback if scheduled here
     → HIT_ENDED
→ post-hit effects and delayed effects
→ cooldown assigned
→ action SP gain/refund
→ ACTION_ENDED
→ terminal/phase check
```

スキルごとに「バフ後に攻撃」「攻撃後にデバフ」「各ヒット後に移動」などの命令列を持たせ、見た目の文章順だけで推定しない。

## 10. ダメージ・回復計算

### 10.1 数値表現

- HP、SP、チェイン、最終ダメージは整数。
- 割合は `basis_points` または既約分数で保持する。
- `floor_mul(value, numerator, denominator)` を唯一の割合乗算関数とする。
- 負値、上限超過、最小1ダメージの有無はダメージ種別プロファイルで定義する。

### 10.2 攻撃・魔法ダメージのパイプライン

2026年8月の韓国実測で一致している主要順序を、次の分離段階として実装する。

```text
S0 = floor(base_attack_or_magic × (100% + stat_increase_total))
S1 = floor(S0 × skill_coefficient)
S2 = floor(S1 × defense_or_magic_resistance_factor)
S3 = floor(S2 × element_factor)
S4 = floor(S3 × special_target_factor)
S5 = critical ? floor(S4 × critical_factor) : S4
S6 = floor(S5 × (100% + outgoing + augmentation + incoming_increase))
S7 = floor(S6 × (100% + current_chain × chain_damage_per_chain))
final = damage_type_finalize(S7)
```

実測では、攻撃値、スキル倍率、属性、部位倍率、クリティカル、与ダメージ増加・増強・被ダメージ増加、チェインを一つにまとめず、途中で小数点以下を切り捨てると表示値へ一致する。防御を含む残りの切り捨て境界は専用トレースで固定し、`ArithmeticProfile` の順序を回帰テストする。

同じ加算グループに属する `outgoing`、`augmentation`、`incoming_increase` は合算してから100%へ加え、グループ外の倍率とは乗算する。スキル固有の「主対象追加」「HP条件」「バフ数条件」「チェイン条件」は、定義された段階へ寄与を追加する。

### 10.3 防御力・魔法抵抗

- 物理は防御力、魔法は魔法抵抗を参照する。
- 表示値へバフ・デバフを適用した後、実効値の上限90%を適用する。
- 90%超の表示値は、防御低下・魔法抵抗低下を受けた後も上限へ残るため捨てない。
- 固定ダメージ、消耗ダメージ、純粋ダメージ、HP割合ダメージは、それぞれの `DamageTypeProfile` が許可した項だけを通す。

### 10.4 属性

属性関係は次のとおりである。

```text
FIRE > WIND > WATER > FIRE
LIGHT ⇄ DARK
```

- 有利属性の基礎倍率は130%。属性ダメージ増加は有利属性の攻撃にだけ加算する。
- 火・風・水の不利属性基礎倍率は50%、中立は100%とする。
- 光と闇は互いを有利として扱い、逆向きも130%である。同属性と無属性は中立とする。
- 属性ダメージ増加を、単純な常時与ダメージ増加へ混ぜない。
- 属性不利と光・闇の境界値は `MATH-06` の現行クライアントトレースを必須回帰試験とする。

### 10.5 クリティカル

```text
effective_crit_rate = clamp(total_crit_rate, 0%, 100%)
excess = max(total_crit_rate - 100%, 0%)
critical_damage += excess × 6
```

超過クリティカル率1%をクリティカルダメージ6%へ変換する。固定・消耗などクリティカル不可の種別は抽選せず、超過変換後のクリティカルダメージも使わない。多段・多対象で抽選を共有するかはスキルの `crit_roll_scope` として保持し、実機検証で設定する。

### 10.6 チェイン

- チェインは対象単位で保持する。
- あるヒットのダメージは、そのヒット開始時点の現在チェイン数を使う。
- 命中したヒットの解決後に、基礎1またはスキル・効果で修正された数だけ増やす。
- 基礎チェインダメージは1チェイン当たり10%。バフ・遺物で変更可能。
- 標準モードのリセット時点はモード規則で定義する。ゴールデンコロシアムでは戦闘終了までリセットしない。
- 回避、0ダメージ、バリア完全吸収、固定ダメージ、DOT、反撃がチェインを増やすかはヒットタグで決める。

### 10.7 回復、バリア、エネルギーガード

回復はダメージと別の算術プロファイルを持ち、攻撃/魔法/最大HP/現在HP/固定値の参照元、クリティカル可否、回復量増減、被回復量増減、回復阻害、最大HP上限を順に適用する。

防御層を同一の「シールド値」にまとめない。

- **ダメージ軽減**: HPへ到達する前に倍率を下げる。
- **保護膜**: 効果定義に従う防御状態。解除タグと貫通タグを持つ。
- **エネルギーガード**: 一時HPとして残量を持ち、所定の優先順でダメージを吸収する。
- **無敵/回避**: 命中またはダメージ適用そのものを無効にする。

解除、貫通、複数層、残量0、失効と同時のダメージをイベント順で処理する。

## 11. 効果システム

### 11.1 効果インスタンス

```text
EffectInstance
  effect_instance_id
  effect_definition_id
  source_unit_id, source_costume_id
  target_id
  polarity: BENEFICIAL | HARMFUL | NEUTRAL
  tags[]
  applied_at_event
  duration_clock, remaining_duration
  stacks, max_stacks
  magnitude
  snapshot_values | dynamic_expression
  refresh_policy
  dispel_policy
  trigger_counters
```

同名効果であっても、発生源別に独立、加算、乗算、強い方のみ、後勝ち、持続延長、スタック加算のどれかを `stacking_group` で指定する。単なる文字列名一致で上書きしない。

### 11.2 必須効果型

- 攻撃力、魔法力、HP、クリ率、クリダメ、防御、魔法抵抗の増減
- 属性ダメージ、与ダメージ、被ダメージ、増強、脆弱、チェインの増減
- 回復、再生、DOT、出血、毒、火傷等
- ダメージ軽減、保護膜、エネルギーガード、無敵、回避、必中
- 挑発、集中攻撃、ロックオン、対象不能
- 沈黙、行動不能、通常攻撃強制、スキル強制
- 反撃、復讐、追撃、攻撃前後トリガー、被弾トリガー
- SP回復/減少/奪取、SP消費増減
- CT増減/初期化/停止
- ノックバック、移動、移動免疫
- 有利効果解除、不利効果解除、能力強化解除、能力弱化解除、解除耐性
- 復活、召喚、変身、交代
- HP、ターン、ヒット数、チェイン、部位攻撃、効果数を条件とするスキル

効果の説明文を実行時に解釈せず、型付き命令へ事前変換する。

## 12. ノックバック、衝突、死亡

### 12.1 ノックバック

ノックバックは次の命令列で処理する。

1. 対象決定。
2. 基礎1ダメージまたはスキル指定ダメージの解決。
3. 対象が生存し、移動可能なら方向ベクトルと距離を計算。
4. 経路、終点、盤外、占有、移動不能を判定。
5. 空きなら移動。占有なら衝突イベント。盤外なら盤外規則。
6. 衝突ダメージ、死亡、占有解放、戻り位置を順に解決。
7. アクション由来のSPを付与。

通常ノックバック行動の衝突係数は被ノックバック対象の最大HP25%である。ルー「白い猫」とテレーゼ「破壊の天使」のようなノックバックスキルは、通常値を流用せず、強化・潜在力を反映した衣装固有係数を `collision_coefficient_bp` として命令へ保持する。移動は1セルずつ経路を走査し、最初の生存味方占有セルの直前まで進めてから、占有者へ防御・物理被ダメージ補正・軽減・バリアを通した非クリティカル衝突ダメージを適用する。盤外、衝突死、反撃対象、バリア消費後のイベント値は実機トレースで最終固定する。

### 12.2 死亡と復活

- HPは0未満へ保持せず0でクランプする。
- `DAMAGE_APPLIED` 後の死亡チェックポイントで `UNIT_DYING` を発火する。
- 致死無効、踏みとどまり、復活を優先順位順に解決し、最終的に `UNIT_DIED` を確定する。
- 死亡時に占有を解放し、予約行動を無効化する。効果は `persists_through_death` を除いて所定のタグを除去する。
- 復活セルが占有されている場合の処理を効果定義に持たせる。
- 同時全滅は全ての同一優先度イベントを処理した後、モードの勝敗規則で判定する。

## 13. 乱数と再現性

- PCG系の明示的な疑似乱数生成器を使い、`seed` とストリーム位置を状態へ含める。
- クリティカル、回避、ランダム対象、ランダム効果、先後決定をストリーム種別で分離するかは、現行クライアントの相関検証後に固定する。
- 各乱数イベントへ `roll_id`、候補順、生成値、閾値、結果を記録する。
- 同じシードで途中保存・復元してもイベント列が一致しなければならない。
- 本番クライアントのシードを推定できない場合でも、確率分布と抽選単位を再現し、シミュレータ内では完全再現可能にする。

## 14. モード別ルール

### 14.1 通常PvE

対象はストーリー、キャラクター/イベントパック、狩猟依頼、一般ステージ、練習戦闘である。

- 3×4、最大5人、味方先手、基準初期SP 15。
- 各味方手番で配置、行動順、コスチュームスキルを変更できる。
- 通常攻撃とノックバックは基礎SPを1獲得する。
- 敵は遭遇定義の行動表、優先条件、ターゲット規則で動く。
- 複数ウェーブは次ウェーブへのHP、SP、CT、効果、チェイン継承をステージ定義に持つ。
- 練習戦闘は所有済み最高バーストまたは指定したバースト3段階を試せるため、開始状態でバースト解放を上書きできる。

### 14.2 鏡戦争

非同期PvPとして、保存された攻撃編成と防御編成を戦わせる。

- 盤面3×4、各5人。通常のキャラクター単位編成と装備・成長を使う。
- 攻撃側が必ず先手で、攻撃側初期SPは5、防御側初期SPは6。
- 最初の攻撃側手番はSP 5のまま開始し、その直前には回復しない。以後、各チーム手番が完了するたびに双方が基礎SPを6回復する。したがって防御側は、攻撃側の第1手番完了後に初期SP 6へ6が加わった状態で最初の行動を開始する。
- 先制発動スキルは戦闘開始時に保存順で処理し、各陣営の初期SPから支払う。
- 攻撃・防御はそれぞれ保存済みの配置、行動順、コスチューム優先を用いる。戦闘中の手動再配置・手動選択は行わない。
- 予約スキルがSP、CT、沈黙、死亡で不可能な場合のフォールバックを現行オート規則に合わせる。
- デスタイム、ターン上限、同時全滅、引き分け、レーティング変化は `MirrorWarRules` に定義する。対戦相手選定とチケットはメタ状態であり、戦闘遷移とは分離する。

### 14.3 ゴールデンコロシアム

シーズン制の非同期PvPであり、通常戦闘とは行動主体と時計が異なる。

- 現行基本盤面は5×5、最大9コスチューム。
- キャラクターではなくコスチューム単位で独立配置し、同一人物の複数コスチュームを同時に使用できる。
- 攻撃用・防御用を分けず、一つの編成を両方に使う。
- 装備は反映しない。結束、潜在力、レベル、刻印、覚醒、コスチューム強化、バーストを反映する。
- 対戦相手を事前表示しない非同期マッチング。戦闘の先手・後手はランダム。
- チーム全員ではなく、先手の1コスチューム、後手の1コスチュームを交互に行動させ、双方の行動枠を解決した後に `all_turn` を1増やす。各陣営の次行動位置を `action_cursor_by_side` として保存し、死亡・行動不能・対象不在によるスキップもイベントとして記録する。スキップ時にカーソルと `all_turn` をどう進めるかはシーズン規則と実機トレースで固定する。
- 現行基本規則ではSP無制限、CTなし、使用可能ならスキルを使う。沈黙またはデスタイムでは通常攻撃へ切り替える。
- チェインは戦闘終了までリセットしない。
- 「剣闘士の加護」は編成全体への効果で、全プレイヤーが同じ候補を使い、ポイント上限内で選ぶ。属性能力、反撃ダメージ、HP、保護膜等を効果システムへコンパイルする。後手には不利を補う追加ポイントを与えられる。
- デスタイム開始、加護候補・上限、先後ポイント差、盤面・人数、SP、CT、チェイン、通常攻撃条件は必ず現在のシーズン定義から読み込む。公式初期案の数値を固定値として使わない。
- 現行運用の週100回、木曜9時開始・水曜24時終了、レーティング/百分位はメタ状態で扱う。自分が能動的に挑戦した結果だけが自分のスコアを変え、他者の対戦相手として呼ばれた結果は所有者スコアを変えない。

### 14.4 魔物追跡者

単一の巨大ボスに対し、部位、条件スキル、複数編成、レベルHPを扱う。

- ボスは本体HPと複数の部位ノードを持つ。部位ごとに座標、弱点倍率、被ダメージ効果、デバフ、チェイン、免疫を持てる。
- ボスの通常/条件スキルは、ターン、HP率、被攻撃回数、チェイン、特定部位への命中、特定効果、編成番号等の条件式と優先度を持つ。
- 初期SPは通常15。手番回復SPはボスごとに異なるため遭遇定義から読み込む。近年の例には5回復と6回復があり、共通値として固定しない。
- ボスはノックバック、沈黙、能力弱化等へ個別の免疫を持つ。全ボス共通と仮定しない。
- レベル上限と各レベルHPはボス開催データから読み込み、固定値にしない。2026-09-01取得の現行「仇怨のキメラ（風）」はLv.1～25である。Lv.1～5は1編成、Lv.6以降は2編成を順番に使用できる。
- 公開データの各Lv.HPは、そのLv.までを含む**累積撃破閾値**である。選択Lv.の表示HPを戦闘中の本体HPとして使い、進捗判定だけはLv.1から各累積閾値と総与ダメージを比較する。内部の区間HPは `threshold[n] - threshold[n-1]` で求め、各Lv.HPをさらに合算してはならない。
- 上位レベルから開始した場合も、与えた累積ダメージで下位レベルを順に自動撃破する。例えばLv.6の累積閾値が3.03億でLv.1～5の閾値が1.60億の場合、2億ダメージ後はLv.1～5撃破済み、Lv.6の残り1.03億となる。`selected_level`、`progress_level`、`battle_hp_remaining`、`segment_hp_remaining` を別々に保持する。
- 編成交代時に本体HPは継承する。SP、CT、チェイン、部位デバフ、DOT、条件スキル回数、フェーズの継承可否はボス定義の `party_handoff_policy` で明示する。
- 挑戦回数自体は無制限。日次報酬と進行は、その日の最高到達/最大ダメージ状態へ更新し、同日再挑戦で記録を改善できる。
- 得点は撃破レベル、次レベルへのダメージ、ボス固有スコアを別項目で保持し、単一報酬値へ早期集約しない。

### 14.5 ギルドレイド

戦闘内の巨大ボス処理は魔物追跡者と同じプリミティブを使うが、個人エピソードとギルド共有進行を分離する。

- 個人戦闘は初期SP、回復SP、部位、条件スキル、ターン上限、即死技を持つ。
- 例として、HP70%以下、攻撃回数、19ターン到達などを条件に、デバフ、SP消費増加、強化、即死を発動できる。
- `GuildRaidPersistentState` はボス段階、共有HP、個人試行、コミット済みダメージ、集計スコアを持つ。
- シミュレーション中の仮結果を共有HPへ即時反映せず、試行確定時に一度だけコミットする。
- 同時更新を再現する場合は戦闘エンジン外で楽観ロックまたはサーバー順序を扱う。

### 14.6 終末の書

- 最大20人の登録キャラクターによる自動ダメージ競技として、通常の5人チーム手番とは別のスケジューラを使う。
- 登場/行動順、使用コスチューム、支援・ボーナス、ボス防御、時間/ターン上限、ダメージ上限を `LastNightRules` に持つ。
- 各行動は同じスキル命令、ダメージ、チェイン、効果システムへ変換する。
- 最終スコアだけでなく、キャラクター別、コスチューム別、ヒット別の寄与を保持する。

### 14.7 悪魔城

- **傲慢の塔**: 指定敵・階層・達成条件・ターン/生存/ダメージ等の得点を通常PvEへ付加する。
- **欲望の塔**: 属性・編成・使用制限など階層固有の制約を合法手と編成検証へ反映する。
- **救済の塔**: ラン開始時の一時成長、コスチューム獲得、遺物、ショップ、ランダム分岐を `RunState` に持ち、戦闘開始時に寄与へコンパイルする。装備非反映など現行モードの成長選択を適用する。
- ラン進行の乱数と戦闘乱数は別ストリームにする。

### 14.8 マルチフェーズ戦闘

2026-08-27更新で導入された現行のフェーズ戦闘を次のように扱う。

- フェーズ移行条件を満たしたチーム手番が終了した後、次の味方手番から次フェーズを開始する。
- ボスへ付与されたバフ・デバフは次フェーズへ継承しない。
- フェーズ戦闘中はデスタイムを適用しない。
- 再挑戦はフェーズを含む戦闘状態を初期化する。
- 有償コンティニュー等のチェックポイント再開は、指定されたフェーズ状態から復元する。
- 味方HP、SP、CT、効果、死亡、編成、盤面の継承はステージの `phase_transition_policy` に明示し、暗黙に全保存または全消去しない。

### 14.9 四魂の盤

四魂の盤は通常のキャラクター編成戦闘をそのまま使うモードではなく、駒購入・合成・配置・向き・床・ショップを持つ独立アダプターとする。

- 外側の状態は所持チップ、ショップ候補、予約、更新費用、駒ベンチ、盤面、ステージ、勝敗を持つ。
- 駒と床は向きを持ち、相対範囲を回転する。
- 戦闘後にショップ更新費用を基準値へ戻すなど、進行規則を戦闘終了イベントへ接続する。
- 毒、再生、エネルギーガードなどは共通効果システムを再利用するが、駒固有能力と攻撃スケジューラは専用定義にする。
- 通常戦闘と同じだと確認できない対象選択、速度、合成能力を流用しない。

## 15. モード規則インターフェース

すべてのモードは次を実装する。

```text
ModeAdapter
  validate_roster(roster, meta_state)
  build_initial_state(encounter, roster, seed)
  next_decision_owner(state)
  legal_actions(state, owner)
  apply_decision(state, action)
  schedule_turn_events(state)
  on_action_complete(state)
  evaluate_phase_transition(state)
  evaluate_terminal(state)
  compute_score(state)
  commit_meta_result(meta_state, terminal_result)
  build_observation(state, viewer)
```

モード差分を戦闘コアの `if mode == ...` へ散らさない。SP、CT、チェイン、時計、行動人数、フォールバック、成長層、勝敗をルールオブジェクトで差し替える。

## 16. 環境API向け状態・行動定義

### 16.1 基本API

```text
reset(scenario_id, roster, seed, options) -> Observation, Info
legal_actions() -> ActionSpace + ActionMask
step(Action) -> Observation, RewardSignals, terminated, truncated, Info
snapshot() -> BattleState
restore(BattleState) -> void
simulate(Action, horizon) -> ProjectedTrace   # 状態を変更しない
```

`step` は一つの意思決定を受け取り、次の意思決定点または終端まで内部イベントを自動解決する。ヒット単位を外部アクションにしない。デバッグ用途では `step_event()` を別に提供する。

### 16.2 観測

観測は完全状態から閲覧者ごとに生成し、情報制約を混ぜない。

- 自陣: 編成、座標、HP、SP、CT、使用可能コスチューム、効果、行動予約。
- 敵陣: モード上見える座標、HP、効果、次行動予告、部位。非公開情報はマスクする。
- 盤面: サイズ、占有、使用不可セル、向き。
- 時間: ターン、ALLターン、フェーズ、編成交代、残り上限。
- ボス: 本体/区間HP、部位状態、条件カウンター、予告スキル。
- モード: 得点中間値、デスタイム、加護、遺物、達成条件。
- 合法手: 編成、順序、行動、コスチューム、バーストの各マスク。

固定長テンソル化のために死者や空セルを0埋めしても、論理状態からは削除しない。ID、マスク、連続値、カテゴリ値の対応表をデータスナップショットへ含める。

現実装の学習用テンソルは、最大32ユニット×56特徴、戦闘全体16特徴、5行動スロットのユニット索引、5×32合法手マスクで構成する。ユニット特徴にはHP・位置・実効能力、与被ダメージ補正、各種軽減、回避、バリア残量、有利/不利効果数、持続・チャージ、CT、チェイン、召喚/部位、主要状態タグを含める。全体特徴には双方SP・生存数・チェイン、モード、ターン、魔物追跡者の現在/選択Lv・残HP・編成を含める。Python単体環境とRust並列環境で別実装を持たず、同じネイティブ生成関数を使う。完全な `BattleState` は `Info` とスナップショットAPIでも取得できる。

### 16.3 行動空間

大きな直積を一つの整数へ潰さず、構造化行動を使用する。

```text
Action
  formation_assignment
  ordered_unit_ids
  command_by_unit
    action_type
    costume_id
    burst_level
    explicit_target_or_part_if_allowed
  commit
```

オートモードでは、事前戦略を登録する `ConfigureFormationAction` と、対戦開始する `StartMatchAction` を分ける。戦闘中に意思決定がない区間は最後まで自動解決できる。

### 16.4 終了・得点出力

```text
TerminalResult
  outcome: WIN | LOSS | DRAW | SCORE_ONLY | ABORTED
  reason
  surviving_units
  turns, actions, phases
  damage_by_source
  healing_by_source
  defeated_boss_level
  carry_damage
  mode_score
  rating_delta_if_committed
```

学習用の報酬設計は本書の対象外とする。ただし、報酬を後から構成できるよう、勝敗だけでなくダメージ、被ダメージ、SP、死亡、ターン、部位、達成条件の原始的な集計値を返す。

## 17. スキル・効果DSL

各スキルをコードへ直書きせず、型付き命令列として表現する。

```yaml
skill_id: example
cost:
  base_sp: 3
  burst_extra_sp: {1: 1, 2: 2, 3: 3}
cooldown: 5
targeting:
  selector: FRONT
  anchor: MAIN_TARGET
  range: [[0,0], [-1,0], [1,0]]
program:
  - op: APPLY_EFFECT
    timing: PRE_HIT
    effect: self_attack_up
  - op: REPEAT_HIT
    count: 3
    body:
      - op: DEAL_DAMAGE
        type: PHYSICAL
        coefficient_bp: 4000
      - op: ADD_CHAIN
        amount: 1
  - op: APPLY_EFFECT
    timing: POST_HIT
    effect: incoming_damage_up
burst_overrides:
  2:
    replace_range: [[0,0], [-1,0], [1,0], [0,1]]
  3:
    replace_hit_count: 5
```

現対象モードで実装する命令は `DEAL_DAMAGE`、`HEAL`、`CONSUME_HP`、`APPLY_EFFECT`、`REMOVE_EFFECTS`、`REMOVE_EFFECTS_BY_TAG`、`ABSORB_EFFECTS_AND_APPLY_STACKS`、`EXTEND_EFFECTS`、`CHANGE_SP`、`CHANGE_SP_PER_SUCCESSFUL_HIT`、`CHANGE_COOLDOWN`、`CHANGE_COSTUME_COOLDOWN`、`KNOCKBACK`、`CONDITIONAL`、`INSTANT_DEATH`、`SUMMON`、`SELF_DESTRUCT`、`APPLY_EFFECT_PER_MATCHING_ENEMY` とする。多段、チェイン増加、バリア、DOT、反撃、復活、被弾/手番終了トリガー、オーラ、領域、加速、変身、標記、暴走は、これらの命令と型付き効果ペイロードの組合せで表現する。

条件式はHP、SP、ターン、チェイン、効果、バフ数、部位、属性、配置、被攻撃回数、編成番号を参照できる。任意コード実行は禁止する。

## 18. 検証と受け入れ基準

### 18.1 ゴールデントレース

現行クライアントで採取した初期状態と行動から、イベント列を保存する。最低限、次の代表ケースを持つ。

- 通常PvE: 通常攻撃、ノックバック、単発/多段/多対象、バフ→攻撃、攻撃→デバフ。
- 対象: Front、Skip、空行循環、挑発、集中、主対象死亡。
- 算術: 物理/魔法/固定/消耗、属性5種、クリ、超過クリ、90%防御、チェイン。
- 効果: 重複、解除、DOT、回復、軽減、保護膜、エネルギーガード、回避、反撃、復活。
- 鏡戦争: 初期SP、毎ターン回復、先制発動、オート不発、デスタイム。
- ゴールデンコロシアム: 先後乱数、1体交互、ALLターン、無限SP、CTなし、チェイン継続、加護。
- 魔物追跡者: 部位、条件スキル、Lv区間、2編成交代、日次保存。
- フェーズ: 遷移手番、ボス効果消去、デスタイム無効、再開。

### 18.2 プロパティテスト

- HPとSPは定義された範囲外へ出ない。
- 同じ状態・行動・乱数状態は同じ遷移を返す。
- 保存・復元前後でハッシュと将来イベント列が一致する。
- 盤面占有は常に一意で、死亡・復活・ノックバック後も破れない。
- 合法手として返した行動は、外部状態が変わらない限り予約時検証を通る。
- 途中丸めを含む算術は、順序を変えた実装を検出できる境界ケースを持つ。

### 18.3 差分診断

差分は最終HPだけでなく、最初に異なったイベントを報告する。

```text
expected seq=184 DAMAGE_APPLIED target=boss_head amount=192607 hp=...
actual   seq=184 DAMAGE_APPLIED target=boss_head amount=192608 hp=...
first divergent stage: CHAIN_MULTIPLIER_ROUNDING
```

受け入れ条件は、決定的ケースで全イベント一致、確率ケースで抽選単位と分布が統計基準内、全モードで保存復元一致である。

## 19. 未確定境界の扱い

公開情報だけで処理順を断定できない箇所を推測で実装しない。現時点の要実機検証は次であり、具体的なケースは [戦闘・実機検証マトリクス](research/browndust2-combat-verification-matrix.md) に定義する。

- 多段・多対象のクリティカル/回避抽選単位
- 属性不利、光・闇、属性ダメージの丸め境界
- 防御/魔法抵抗の負値領域と固定・消耗ダメージの除外項
- 同種効果の重複、解除、失効、スナップショット
- ダメージ、効果、反撃、死亡、復活の同値優先順位
- ノックバックの衝突・盤外・死亡・バリア
- ターゲット再取得、主対象死亡、強制対象競合
- SP、CT、持続ターンの正確な更新点
- 各モードの同時全滅、引き分け、デスタイム、編成交代継承

これらは `ArithmeticProfile`、`EventPriorityTable`、`TargetingProfile`、`KnockbackProfile`、`ModeRules` の一か所へ閉じ込め、実機確定後にデータまたは表を置換する。

## 20. 実装順序

1. 固定小数点算術、状態、イベントキュー、乱数、保存復元。
2. 3×4盤面、Front/Skip、通常攻撃、SP、物理/魔法ダメージ、死亡。
3. スキルDSL、CT、バフ/デバフ、チェイン、クリティカル、属性。
4. ノックバック、バリア、エネルギーガード、回避、反撃、復活。
5. 通常PvEと現行クライアントのゴールデントレース一致。
6. 鏡戦争アダプター。
7. ゴールデンコロシアム専用スケジューラと加護。
8. 魔物追跡者の部位、条件スキル、レベル区間、複数編成。
9. ギルドレイド、終末の書、悪魔城、マルチフェーズ。
10. 四魂の盤の専用進行・盤面アダプター。

各段階は対象トレースが完全一致してから次へ進む。コスチューム全件投入は、命令セットと代表ケースが確定した後に行う。

## 21. 2026-09-01実装スナップショット

現リポジトリは、本書のうち今回対象とする通常戦闘、鏡戦争、魔物追跡者を実行可能な状態にしている。実装済み範囲は次のとおりである。

- Rust製の決定論的戦闘コア、整数固定小数点算術、イベントログ、シード付き乱数、状態保存・復元。
- 通常戦闘と鏡戦争の3×4盤面、行動計画、Front/Skip、範囲、SP、CT、チェイン、主要ダメージ・効果命令、死亡・復活・反撃・回避・バリア・DOT。
- 魔物追跡者の共有本体HP、攻撃可能部位、弱点、通常スキル列、相手行動直後の条件スキル割り込み、累積Lv.閾値、2編成交代。
- 現行外部データからの61体の★5プレイアブルキャラクター、155コスチューム、召喚4種、5ボススキル、合計12,509スキル派生のSQLite化。全派生は型付き命令列へ変換済みで、原文、取得元、取得日、SHA-256を保存する。
- 全衣装の意味タグを、直接命令だけでなく条件分岐、被弾/手番終了トリガー、オーラ/領域、召喚先スキルまで再帰的に照合する生成物検査を備える。12,509派生の実行可能性、コンパイル診断ゼロ、意味対応ゼロ欠落を同期ごとに確認する。
- 現行スキルの型付き特殊処理として、標記による回避無効、全残SP消費型暴走、効果数条件、独立上限スタック、デバフ吸収、加速時チェイン閾値、ターン終了回復/SP、付与効果除去、オーラ/領域の再付与、変身状態、召喚元能力継承、召喚順序、衣装強化を継承する召喚スキル、衣装別ノックバック衝突係数を実装する。
- 強化段階、潜在力マスク、バースト解放/使用段階、コスチューム結束先、装備補正をシナリオのロードアウトから差し替えられる。レベル100・覚醒済み・最大強化のシナリオ生成器を備える。
- Gymnasium/TorchRL互換環境、ネイティブ並列環境、合法手マスク付きTransformer Actor-Critic、GPU混合精度PPO、評価器、GUIを分離して実装する。行動ヘッドは固定スロットだけでなく、そのスロットを担当する実ユニットのTransformerトークンを参照する。観測/モデル構造IDをチェックポイントへ保存し、不一致モデルを拒否する。GUIは未起動なら学習ホットパスへ一切入らず、人間側と学習済み方策側を指定して対戦できる。

ただし、型付き命令へ変換できたことは、現行ゲームクライアントとの全イベント一致を意味しない。公開データにない丸め境界、同値イベント順、確率抽選単位、効果重複、ノックバック境界等は、実機トレースが得られるまで [検証マトリクス](research/browndust2-combat-verification-matrix.md) の `CLIENT_TODO` とする。自動テストのみ通った項目と実機一致済み項目を混同して「完全再現」と判定してはならない。
